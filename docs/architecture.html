How it's built · dbt + DuckDB

From raw to report in five layers. Every layer tested.

The whole platform is one dbt project. Raw tables land, staging cleans them, intermediate holds the business logic, marts hold one grain each, and the serving layer is what people and AI agents query. This page is generated from dbt's own model graph, so it always matches the code.

Entity-relationship diagrams

Revenue is a star schema.

Three conformed dimensions fan out to four facts through surrogate keys, so any fact can be sliced by account, product or rep the same way.

People data stays behind one door.

dim_employee and the headcount fact are private to People Analytics. Everyone else reads a secure view or a suppressed aggregate, and the revenue domain joins in through a bridge that carries keys only.

erDiagram

    DIM_SALES_REP ||--o| BRIDGE_EMPLOYEE_SALES_REP : sales_rep_key
    DIM_EMPLOYEE  ||--o{ SECURE_ROLE_VIEWS         : "one view per role"
    DIM_EMPLOYEE  ||--o{ RPT_PEOPLE_METRICS        : "aggregated, n >= 5"
    FCT_HEADCOUNT_MONTHLY ||--o{ RPT_PEOPLE_METRICS : "month x department"

    DIM_EMPLOYEE {
        string employee_key PK
        string employee_name "PII"
        string work_email "PII"
        date date_of_birth "PII"
        string department
        string job_level
        number base_salary "Restricted"
        number compa_ratio "Restricted"
        string gender "Restricted"
        string current_leave_type "Restricted"
    }
    FCT_HEADCOUNT_MONTHLY {
        date month_end
        string department
        string region
        number headcount
        number hires
        number exits
    }
    BRIDGE_EMPLOYEE_SALES_REP {
        string employee_key FK

    SECURE_ROLE_VIEWS {
        string role "hr, finance, sales_manager_emea, analyst"
    }
    RPT_PEOPLE_METRICS {
        string grain "department, level x gender, month"
        boolean is_suppressed
    }
